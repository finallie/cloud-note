## 监控

使用prometheus、grafana监控MySQL

### 监控指标

- 连接 当前连接数、当前活动连接数、最大连接数
- 查询 每秒查询数、慢查询数、查询缓存命中率
- 事务 每秒提交数、每秒回滚数、事务等待时间
- 缓存 使用的缓冲池大小、命中率、脏页数
- 磁盘 IO 每秒读写字节数、每秒读写次数、磁盘使用率
- 锁 每秒锁等待数、锁等待时间、死锁数
- 错误 错误数、警告数、异常数
- 复制 状态、延迟、错误数
- 资源 使用的CPU、内存、磁盘空间

### 系统数据库

- mysql 用户权限、用户信息、非表结构元数据（如存储过程、函数定义）
- information_schema 表机构元数据
- performance_schema 性能监控
- sys 提供一些便利的视图和存储过程，基于其他数据库

## 硬件与操作系统优化

通常的瓶颈在于cpu、内存

- cpu
- 内存（缓存减少磁盘io）
- 磁盘（ssd（更快的顺序io、明显更快的随机io、更强的并发能力）、raid）
- 网络

## 表结构设计

选择正确的数据类型

- 更小的一半更好（更少的磁盘、内存、缓存）
- varchar的长度尽量小（join_buffer、排序缓存按照最大长度分配内存）
- 使用简单的数据类型（比如整数比较比字符串更快，时间数据应该用内置时间类型不用字符串，ip地址用整数不用字符串）
- 尽量不存储null值（null值需要额外的存储空间，且不利于优化）

### char vs varchar

- char在存储时用空格填充长度，提取时消除空格
- char在早先版本（使用redundant行格式）是定长字节的，使用n*字符集最大字节数存储
- char在新版本（使用compact行格式）并使用变长字符集时是变长的

### 枚举类型

优点：

- 使用整数存储，节省空间
- 可读性好

缺点：

- 修改枚举值需要修改表结构
- mysql私有特性，不利于移植
  
### 时间类型

- 默认精度为秒，timestamp有2038问题
- timestamp默认not null，会自动更新为当前时间

## 索引

- 创建正确索引避免全表扫描、排序、临时表
- 使用analyze table更新统计信息
- 使用optimize table修复碎片

### 索引失效原因

- where条件中对索引列进行了函数操作
- 非前缀模糊查询
- 违反联合索引最左前缀原则
- 索引基数太低
- or条件两边都必须用到索引

## 查询语句优化

- 不要使用select *（会使join_buffer、排序缓存需要更多内存）
